The bug to catch — exhibit A

The conversion shifts days, not hours

// what the M does today
Date.AddDays( [AnsweredOnUTC], [UtfOffsetHours] )
// UtfOffsetHours = -5  →  AddDays treats it as -5 DAYS

UTC      2026-06-03 12:00
result  2026-05-29 12:00   // 5 days early
should   2026-06-03 07:00   // 5 hours earlier
5–6days every date is shifted back

6 tables, ~13 date columns. In FactResponses alone, 2,883 rows are wrong (offsets −6 and −5) — counts from the trimmed sample. Every "completed this week", deadline and trend is off by a week.

A common assumption to clear up

Power BI does not localize timestamps for you

  • A stored datetime shows as-is to everyone — Houston, Tokyo, same value. Only the format follows the viewer's locale, never the instant.
  • Power Query runs once, at refresh, on the gateway/Service (UTC) — not per viewer. It has no idea who'll open the report.
  • So conversion is a real task you build deliberately. Do nothing and everyone just sees raw UTC.

You're not reinventing a platform feature — UTC→local genuinely has to be done somewhere on purpose.

The one decision that drives everything

Whose time zone — the place, or the person?

The place

The plant where the reading was logged. A property of the record — finite, known, already on every row. Everyone sees the same timestamp for an inspection.

The person

The location of whoever opens the report. Different for every viewer — and unknowable at refresh time.

Pick this first. Everything — the method, the effort, even whether it's possible — follows from it.

Option C can't be done at refresh (SQL or PQ) at all — the data is baked once for everyone. It'd require a viewer-selected zone parameter. For inspection records, Option A is almost certainly what you want.

Daylight saving — don't hand-code it

A fixed offset can't know the season. A named zone can.

Fixed offset (today)

UtfOffsetHours = −6

Can't tell CST (−6) from CDT (−5). Wrong half the year. The −5 / −6 split you already have hints at this.

Named zone (SQL)

AT TIME ZONE
'Central Standard Time'

The engine reads the OS zone database and flips CST↔CDT by date. Japan = no DST, handled automatically. You encode nothing.

You never maintain DST rules — you just name the zone. That's the whole reason named zones beat a stored number.

Why "global company" doesn't complicate it

You convert for the place, not the person

~a dozenplant zones to support

Not the whole world — just the zones your sites sit in (Central, Eastern, Tokyo…). That list already lives on each record as TimeZone.

Two people — one in Houston, one in Tokyo — both see a La Porte inspection at the same La Porte local time. The viewer's location never enters the maths, so a scattered, worldwide workforce doesn't complicate it at all.

Where to do the conversion

Two homes — one is clearly better

Best — in SQL 
-- in Responses_Flat_v, DST-correct
Response_Date
  AT TIME ZONE 'UTC'
  AT TIME ZONE 'Central Standard Time'

Handles DST · also fixes the broken query folding (refresh speed) · one place.

Quick fix — Power Query 
// correct units, no DB change
[AnsweredOnUTC]
  + #duration(0, [UtfOffsetHours], 0, 0)

Fixes the day-shift immediately — but uses the fixed offset, so still no DST. Good as an interim.

Carrying timezone-aware values instead? DateTimeZone.SwitchZone(DateTime.AddZone([…UTC], 0), [offset]) — same accuracy, more explicit zone intent.

Step 0 — before trusting any of it

Is the source actually UTC?

The model assumes it — but that assumption lives only in a column rename (Response_Date → AnsweredOnUTC). That's the previous developer asserting it, not proof.

If it's UTC

Convert outward once to plant-local. Fix the units / move to SQL. Done.

If it's already local

Applying an offset is double-converting — wrong no matter how you fix the formula. Use it as-is, or convert local→UTC first.

Confirm with whoever owns the GoPlant database. Everything downstream depends on this one answer.

The path

If we had to recommend

  • 1 · Confirm the source is UTC (step 0).
  • 2 · Decide the requirement — almost certainly Option A, plant-local.
  • 3 · Convert in SQL with AT TIME ZONE named zones → DST handled, folding restored.
  • 4 · Interim: if SQL access lags, the Power Query #duration fix stops the day-shift bleeding today.

The hard part — anchoring in UTC with zone metadata — you've already done. This is finishing the last mile correctly.

The one thing to remember

Convert for the place, anchor in UTC.

Keep the truth in UTC, convert each record to its plant's zone with a named zone so DST takes care of itself, and never make the answer depend on who's looking. Fix the day-shift first — then move the conversion to SQL when you can.
