Storage groups form a tree

  • Parent — one step up. Relative to where you are; changes at every level.
  • Level1 — the top of the branch (the plant). Same for everything beneath it, no matter how deep.
  • Leaf — the bottom. Where assets, tasks and checklists are actually tagged.

30 of 92 groups sit 3+ levels deep — so "parent" and "Level1" are genuinely different things here.

The core mismatch

Access is granted at the top.
Data is tagged at the bottom.

Users are mapped to

Plants

Jonas → La Porte (one top-level ID: 51).

Assets are tagged to

Leaf groups

A Plant, Northside, Southside … (IDs like 68, 86, 87).

So "give Jonas La Porte" has to fan downward from one top node to every leaf beneath it. Every wrong version of this got that fan-out wrong.

What was there before

A security table wired to every dimension

  • One RLS table, copied 6 times (RLS (2)…(7)).
  • Each copy joined to a dimension with an active, bi-directional security relationship.
  • The copies existed only to dodge the ambiguity errors you hit when one table fans out to many.

The instinct was right

They'd correctly realised every dimension needs the filter to reach it. The goal was sound — the mechanism was the problem.

Why it broke — exhibit A

The mapping holds parent IDs (51); assets hold leaf IDs (68, 86…). Joining one to the other matches almost nothing — so the design quietly hid 362 of 363 assets.

The principle that fixes everything

RLS rides relationships,
not table references

  • A filter on a secured dimension flows downhill to the facts related to it — automatically.
  • It does not chain through one rule mentioning another table. Inside a rule, other tables are read unfiltered.
  • So each dimension must resolve the user itself — and facts need no rule at all.

This is why the first re-write still leaked: the rules referenced each other and assumed the filter carried over. It didn't — every user saw 87 of 92 groups instead of 8.

Why we secure every dimension

Some facts never touch the storage-group dimension

88Jonas should see

Round Completion has no relationship to DimStorageGroup — it only hangs off DimTask, DimRound… Securing those dimensions is the only thing that reaches it.

Securing dimensions isn't slicer tidiness — it's how the filter reaches facts that don't connect to storage groups directly.

The fix

One self-contained rule per dimension

// Step 1 — the plants this user is granted (top-level / Level1 IDs)
VAR UserParentSGs =
    SELECTCOLUMNS( FILTER( RLS, RLS[UPN] = USERPRINCIPALNAME() ), "SG ID", RLS[SG ID] )
// Step 2 — expand each plant to every group beneath it, via Level1
VAR UserGroups =
    SELECTCOLUMNS( FILTER( DimStorageGroup,
        DimStorageGroup[Level1StorageGroup_ID] IN UserParentSGs ), "StorageGroup_ID", DimStorageGroup[StorageGroup_ID] )
RETURN
    [StorageGroup_ID] IN UserGroups   // keep the row if its group is in the set

No duplicate tables. No bi-directional relationships. Each rule resolves USERPRINCIPALNAME() on its own and keys on Level1, so it captures the whole branch at any depth.

How to test it

"View As" needs both boxes — here's why

✕✕EverythingNo role = no security applied
✓✕EverythingIdentity set, but no rule reads it
✕✓NothingRule runs as you — not in the mapping
✓✓Jonas's 8 / 363Security on and identity = Jonas

Role = the switch (turn security on). Other user = the identity (USERPRINCIPALNAME()). Dynamic RLS needs both — a static role would need only the switch.

The one thing to remember

Filters travel through relationships.

Secure each dimension on a path to your data, resolve the hierarchy with Level1, and let the facts follow. No duplicate tables, no bi-directional cross-filter — just rules that match the shape of the tree.
